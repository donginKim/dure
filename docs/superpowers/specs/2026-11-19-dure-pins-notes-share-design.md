# 대화 핀, 메모 마크다운 보기, 조율 에이전트 공개 범위

2026-11-19. 브랜치 `feat/dure-pins` (감사 기록 브랜치 `feat/dure-audit-log` 위에 쌓음: 둘 다 DB 구조를 바꿔 번호가 겹치지 않게).

세 가지 작은 변경을 한 묶음으로 한다. 서로 기대지 않으므로 따로 만들고 따로 확인할 수 있다.

## 1. 대화 핀

### 왜
긴 대화에서 다시 보고 싶은 글을 스크롤로 찾는 일이 번거롭다. 사용자는 그 자리에 다시 가서 **내용을 확인**하려 한다 (앞뒤 맥락 전체를 되살리려는 것이 아니다). 자주 보는 것은 지금 손으로 메모에 옮겨 적는다.

### 목표
- 대화의 글에 핀을 꽂고, 핀 목록에서 눌러 그 글을 바로 본다.
- 대화가 새로 시작돼도 (설정 "TODO 마다 새 대화", 대화 압축, 두레 다시 켜기) 핀은 남고 내용을 볼 수 있다.
- 핀에서 메모로 한 번에 보낸다.

### 하지 않는 것
- 지난 대화를 다시 불러와 그 자리와 앞뒤 글을 보여 주기.
- 모든 워크스페이스의 핀을 한곳에 모은 화면.
- 에이전트가 핀을 보거나 만들기. 함께하는 사람에게 핀 보이기.
- 핀 이름 고치기, 핀 순서 바꾸기.

### 실패로 보는 것
- 대화가 바뀌자 눌러도 아무 일도 없는 죽은 핀이 생기는 것.
- 핀을 누르면 대화가 맨 아래로 다시 끌려 내려가는 것.

### 방식 (세 가지 중 "가" 를 사용자가 골랐다)
- **가. 자리 + 내용 사본 (고름)**: 핀이 글의 id 와 글 내용을 함께 담는다. 화면에 그 글이 있으면 그 자리로 가고, 없으면 담아 둔 내용을 보여 준다. 대화가 바뀌어도 죽지 않고, 일이 작다. 지난 대화는 앞뒤 글을 못 본다.
- 나. 자리만: 가장 단순하지만 대화가 새로 시작되면 핀이 죽는다. 기본 설정에서 TODO 하나마다 대화가 바뀌므로 쓸 수 없다.
- 다. 지난 대화까지 다시 열어 이동: 언제든 원래 자리로 가지만 기록 파일을 다시 읽어 화면에 끼워야 해 일이 크다. 목적(내용 확인)에 비해 과하다.

### 확인한 지금 구조
- 대화 항목마다 고정 id 가 있다 (Claude Code 기록의 uuid). `src/core/chat/transcript.ts`
- 화면에는 지금 대화의 최근 400개만 온다. `src/core/chat/chatService.ts` 의 `MAX_ITEMS`
- 대화 화면은 맨 아래 붙기만 있고 특정 항목으로 가는 기능은 없다. `src/renderer/components/ChatPane.tsx`
- 워크스페이스 대화와 조율 대화가 같은 `ChatPane` 을 쓴다.

### 동작
- **꽂을 수 있는 글**: 에이전트의 글, 내 글, 두레가 넣은 글(알림, 다른 에이전트가 보낸 메시지), 슬래시 명령의 출력. 접힌 작업 줄("명령 N개 실행함")과 안내 줄(중단됨, 압축됨)은 안 된다.
- **꽂기**: 글에 마우스를 올리면 핀 단추가 보인다. 누르면 꽂히고, 꽂힌 글에는 작은 핀 표시가 남는다. 다시 누르면 빠진다.
- **목록**: 대화 화면 위쪽에 "핀 N" 단추. 누르면 목록이 열린다 (새 것부터). 줄마다 글의 첫 줄(60자), 누가 쓴 글인지, 꽂은 시각. 핀이 없으면 단추는 흐리게 "핀" 만 보이고, 눌렀을 때 꽂는 방법을 한 줄로 알려 준다.
- **가기**: 줄을 누르면
  - 그 글이 지금 화면에 있으면: 목록을 닫고 그 글이 가운데 오게 스크롤한 뒤 잠깐 강조한다. 이때 "맨 아래 붙기" 는 꺼진다 (새 글이 와도 끌려 내려가지 않는다. 이미 있는 "아래로" 단추로 돌아간다).
  - 없으면 (지난 대화, 400개 밖): 그 줄이 목록 안에서 펼쳐져 담아 둔 내용을 마크다운으로 보여 주고, "지난 대화의 글입니다. 담아 둔 내용을 보여 줍니다" 라고 적는다.
- **줄의 단추**: "메모로 보내기" (제목은 첫 줄, 본문은 담아 둔 내용인 새 메모를 만든다. 만든 뒤 "메모에 담았습니다" 를 보인다), "빼기".
- 워크스페이스를 지우면 그 핀도 지운다.

```
┌ 대화 ──────────────────────────  [핀 3] ┐
│  ┌ 핀 ─────────────────────────────┐   │
│  │ API 형식이다. 이미 이대로 구현…  │   │
│  │ 조율@민지 · 10:17   [메모로] [빼기]│   │
│  │ 화면과 API 연동 확인을 끝내고…   │   │
│  │ 에이전트 · 09:41    [메모로] [빼기]│   │
│  └──────────────────────────────────┘   │
│  에이전트의 글 …………………………… 📌    │
```

### 담는 것
표 `pins`: id, workspace_id, item_id, kind(누가 쓴 글인지), title(첫 줄), body(담아 둔 내용), created_at. 한 워크스페이스에서 같은 글은 한 번만 (workspace_id + item_id 가 하나). 본문은 5만 자, 워크스페이스마다 200개까지 (넘으면 꽂지 못하고 이유를 보인다).

### 만드는 사람에게 맡기는 것
- 본문을 화면이 보내게 할지, 코어가 대화 기록에서 읽게 할지 (어느 쪽이든 길이는 코어에서 자른다).
- 강조의 모양과 시간, 목록이 열리는 모양(덮개인지 옆 칸인지). 지금 화면의 색과 모양을 따른다.
- 다른 에이전트가 보낸 메시지처럼 대화 기록이 아닌 곳에서 온 글의 id 를 무엇으로 삼을지.

## 2. 메모를 마크다운으로 보기

### 왜
메모를 열면 입력칸 하나라 `##`, `**`, 표가 기호 그대로 보여 읽기 불편하다. (메모는 md 파일이 아니라 두레 DB 에 글자 그대로 들어 있다. 저장은 그대로 두고 보이는 모습만 바꾼다.)

### 동작
- 메모를 열면 **보기**가 먼저 뜬다: 대화 화면이 쓰는 `Markdown` 부품으로 그린다 (제목, 목록, 표, 코드). 링크는 지금처럼 누를 수 없는 글자다.
- "고치기" 를 누르면 지금의 입력칸으로 바뀌고, "보기" 로 돌아온다. 적는 대로 저장되는 것은 그대로다.
- 새 메모와 본문이 빈 메모는 바로 고치기로 연다.
- 에이전트가 메모를 읽고 쓰는 방식, 찾기, 저장 형식은 바꾸지 않는다.

## 3. 조율 에이전트의 공개 범위

### 왜
조율 에이전트가 다른 사람의 에이전트에게 기획서(자료)를 보내려 하면 "이 워크스페이스를 공개해 달라" 고 하는데, 화면에 조율 에이전트를 공개할 곳이 없다. 지금은 계획안에서 일을 나눠 줄 때 그 사람에게만 저절로 공개된다 (`peerService.allow`). 일을 나눠 주지 않은 사람에게는 공개할 수 없고, 저절로 공개된 것을 다시 닫을 수도 없다.

### 확인한 지금 구조
- 코어는 조율 에이전트도 공개 범위를 가질 수 있다 (`setSharing`, `visibleTo`, `publishNow` 가 가리지 않는다).
- "함께" 탭의 목록이 일하는 워크스페이스만 받는다 (`ProjectView` 가 `workspaces` 만 넘긴다. 조율까지 든 `everyone` 도 이미 받고 있다).

### 동작
- "함께" 탭의 "내 워크스페이스의 공개 범위" 목록 맨 위에 **조율 에이전트** 줄을 넣는다. 다른 줄과 같은 선택지 (공개 안 함, 모두에게, 고른 사람에게).
- 그 줄에 한 줄 설명: "공개하면 그 사람의 에이전트와 메시지와 자료(기획서 등)를 주고받습니다. 일을 나눠 준 사람에게는 저절로 공개됩니다."
- 조율 에이전트가 아직 한 번도 켜지지 않아 워크스페이스가 없으면 줄을 보이지 않는다.
- 공개돼 있지 않아 막혔을 때 에이전트에게 가는 글을 고친다: "사용자에게 프로젝트의 함께 탭에서 공개해 달라고 하라" 로, 어디서 하는지 알 수 있게.
- 일을 나눠 줄 때 저절로 공개되는 것은 그대로 둔다.

## 확인
- 코어: 핀 저장소의 시험 (꽂기, 같은 글 두 번, 상한, 워크스페이스를 지우면 함께 지워짐). 공개 범위는 조율 워크스페이스에 대한 시험 하나.
- 화면: 분리된 데이터 폴더로 띄운 두레에서 직접 확인한다. 핀 꽂기 → 스크롤해 올라간 뒤 핀으로 이동 → 새 대화가 시작된 뒤 그 핀을 눌러 내용이 펼쳐지는지 → 메모로 보내 마크다운으로 보이는지. 함께 탭에서 조율 줄이 보이고 바뀌는지.
