# 두레(dure) 버전 1 설계

작성일: 2026-11-11

표기: **[사용자 결정]** 은 사용자가 대화에서 직접 정한 것, **[작성자 판단]** 은 설계 작성자가 정한 기본값이라 사용자가 뒤집을 수 있는 것, ⚠️ 는 아직 실측으로 확인하지 않은 추정이다.

## 1. 의도

두레는 ADE(Agentic Development Environment)다. 코딩 에이전트 여러 개를 워크스페이스별로 띄워 병렬로 굴리고 감독하는 데스크톱 앱이다.

사용자는 지금 Orca를 쓴다. 편하지만 두 가지가 아쉽다.

1. 워크스페이스가 서로 단절돼 있다. 프론트와 백엔드처럼 한 세트로 움직여야 하는 워크스페이스의 에이전트들이 서로 대화하고 자료를 주고받으며 맞물려 개발하지 못한다.
2. 에이전트가 세운 계획(TODO)이 대화 속에 묻힌다. 별도 화면에 늘 보이지 않고, 사용자가 손으로 처리한 일을 반영하거나 계획을 고쳐 에이전트의 방향을 바꿀 수 없다.

두레는 이 둘을 해결하는 것이 존재 이유다. 이름은 마을 사람들이 모여 함께 일하던 공동 노동 조직 "두레"에서 왔다.

## 2. 버전 1이 완성됐다고 볼 두 장면 [사용자 결정]

### 장면 1: 프론트에 말하면 백엔드까지 알아서

1. 사용자가 프론트 워크스페이스를 선택하고 "이 DB 값을 화면에 그려줘"라고 말한다.
2. 프론트 에이전트가 백엔드 워크스페이스의 에이전트를 깨워 대화한다. 필요한 API와 응답 형식을 합의한다.
3. 백엔드 에이전트가 DB를 호출하는 코드를 만들고 서버를 띄운다.
4. 프론트 에이전트가 그 API를 호출해 화면을 그리고 테스트한다.
5. 각 에이전트가 커밋 메시지를 써둔다. 커밋은 실행하지 않는다.
6. TODO 패널에 남은 일이 "커밋", "push", "개발서버 배포"처럼 사용자 몫으로 적혀 보인다.

### 장면 2: 기획서를 프로젝트에 주면

1. 사용자가 프로젝트를 선택하고 기획서를 보여준다.
2. 조율 에이전트가 필요한 워크스페이스(백엔드, 프론트 등)를 판단해 제안한다.
3. 사용자가 제안을 고치거나 그대로 승인한다. 승인 뒤에만 워크스페이스가 만들어진다.
4. 조율 에이전트가 기획서에서 개발 TODO를 뽑아 프로젝트와 워크스페이스별로 자동 작성한다.

## 3. 목표, 비목표, 반목표

### 목표 (버전 1 범위)

1. 껍데기: 앱 창, 프로젝트·워크스페이스 2단 목록, git worktree 관리, 터미널, 에이전트 실행
2. 두레 코어: 상태 저장과 에이전트용 MCP 통로
3. TODO 패널: 사용자와 에이전트가 함께 고치는 계획
4. 에이전트 간 대화: 깨우기, 메시지, 자료 공유
5. 프로젝트 조율: 기획서에서 워크스페이스 제안과 TODO 작성
6. DB: 프로젝트 단위 연결, 조회 패널, 에이전트용 조회 도구
7. 워크스페이스 요약과 자동 이름

### 비목표 (버전 1에서 하지 않음)

- 내장 브라우저 패널, diff 뷰, 자동화 등 나머지 Orca 기능. 버전 1 이후에 만든다. [사용자 결정: 최종적으로는 Orca 기능 거의 전부가 있어야 한다]
- Windows, Linux 지원 [작성자 판단: macOS 먼저]
- 원격 장비(SSH, 클라우드)의 워크스페이스. 한 PC 안에서만 동작한다.
- 여러 사용자 공유, 클라우드 동기화
- Claude Code와 Codex 외의 에이전트

### 반목표 (기능이 돌아가도 이러면 실패)

- 에이전트가 사용자 허락 없이 커밋 실행, push, 배포를 한다.
- 두레의 DB 기능을 통해 데이터가 쓰이거나 지워진다.
- 에이전트끼리 메시지를 끝없이 주고받아 토큰 비용이 통제 없이 불어난다.
- 사용자가 손으로 고친 TODO를 에이전트가 덮어쓴다.
- DB 비밀번호 같은 접속 정보가 에이전트 대화, TODO, 로그에 드러난다.
- 두레가 사용자 저장소 안에 자기 설정 파일을 남겨 작업 트리를 더럽힌다.

## 4. 제약

- 바닥부터 새로 만든다. 기존 오픈소스 ADE 위에 얹지 않는다. [사용자 결정]
- Electron 데스크톱 앱이다. 가벼움보다 내장 브라우저 같은 기능을 우선한다. [사용자 결정]
- Claude Code와 Codex를 처음부터 함께 지원한다. [사용자 결정]
- 스택 [작성자 판단, 사용자가 제안을 수락]: TypeScript, React + Vite, xterm.js + node-pty, SQLite, git 명령 직접 호출, pnpm. Monaco는 diff 뷰를 만들 때 들인다.
- 코드는 이 저장소(`개인 챌린지`)에 둔다. [작성자 판단]
- 완성 기준은 사용자 PC에서 직접 빌드한 `.app` 이 돌아가는 것이다. 코드 서명, 공증, 자동 업데이트, 외부 배포는 버전 1 범위가 아니다. [작성자 판단]

## 5. 개념 모델

- **프로젝트**: 함께 움직이는 워크스페이스의 묶음. 서로 다른 저장소의 워크스페이스를 한데 묶을 수 있다. 보통 프론트와 백엔드 한 세트가 한 프로젝트다. [사용자 결정]
- **워크스페이스**: 한 저장소의 git worktree 하나와 그 안에서 도는 에이전트 세션, 터미널의 묶음.
- **조율 에이전트**: 프로젝트마다 하나 있는 에이전트 세션. 프로젝트에 내려진 지시를 나누고, 진행을 지켜보고, 끝나면 종합해 보고한다. [작성자 판단, 사용자 확인]
- **TODO**: 두레가 원본을 쥐는 계획 항목. 프로젝트 범위와 워크스페이스 범위가 있다.
- **메시지**: 워크스페이스(또는 조율 에이전트) 사이에 오가는 글. 스레드로 묶인다.
- **자료**: 프로젝트 안에서 공유되는 작업 결과, 결정사항, API 스펙 등. 파일은 복사하지 않고 같은 PC의 절대 경로를 링크로 건넨다. [사용자 결정]

## 6. 구조

```
┌────────────────────── Electron 앱 ──────────────────────┐
│  화면 (React)                                            │
│   프로젝트·워크스페이스 목록 │ 터미널 │ TODO │ 대화 │ DB   │
│            ▲ IPC                                         │
│  두레 코어 (메인 프로세스, Electron에 의존하지 않는 모듈)   │
│   상태(SQLite) │ worktree │ PTY │ 메시지 배달 │ DB 조회    │
│            ▲ MCP (localhost HTTP, 워크스페이스별 토큰)     │
└────────────┼────────────────────────────────────────────┘
   에이전트 CLI (Claude Code / Codex), 터미널(PTY) 안에서 실행
```

핵심 판단 [작성자 판단]:

- **두레 코어가 모든 상태의 원본이다.** 화면과 에이전트는 둘 다 코어의 손님이다. 코어는 Electron에 의존하지 않는 모듈로 짜서 Electron 없이 단위 테스트하고, 나중에 별도 프로세스로 떼어낼 수 있게 한다.
- **에이전트는 터미널에서 CLI 그대로 돈다.** 사용자는 Orca처럼 에이전트 화면을 직접 보고 끼어들 수 있다.
- **에이전트와 코어의 통로는 MCP 하나다.** 두 에이전트 모두 MCP를 지원하므로 같은 도구 집합이 양쪽에 똑같이 보인다. 코어는 localhost에서 MCP 서버를 열고, 워크스페이스마다 다른 토큰을 줘서 어느 워크스페이스의 호출인지 가린다.
- **에이전트 설정은 실행할 때 인자와 환경변수로 넘긴다.** 사용자 저장소 안에 `.mcp.json` 같은 파일을 쓰지 않는다. Claude Code는 `--mcp-config`(두레 폴더의 파일), `--append-system-prompt`, Codex는 `-c mcp_servers.dure.*`, `-c developer_instructions` 로 된다(0단계 실측, Codex는 접속과 지침 주입까지).
- **설정 주입이 인자와 환경변수로 안 될 때의 물러서는 순서**: (1) 저장소 밖 두레 전용 폴더에 워크스페이스별 설정 파일을 두고 에이전트가 그것을 읽게 한다. (2) 그것도 안 되면 사용자 전역 설정에 넣을 수정안을 화면에 보여주고 사용자가 직접 적용한다. 두레가 사용자 전역 설정 파일을 몰래 고치지 않는다. 어떤 경우에도 사용자 저장소 안에는 쓰지 않는다. 이 원칙이 "Codex 동시 지원"보다 우선한다.
- **상태 저장은 SQLite 파일 하나다.** 위치는 `~/Library/Application Support/dure/`.

## 7. 구성 요소별 동작

### 7.1 껍데기

- 왼쪽 목록은 프로젝트 아래에 워크스페이스가 달린 2단 구조다. 어느 단을 선택했느냐가 지시 대상을 정한다. [사용자 결정]
  - 워크스페이스를 선택하고 말하면 그 워크스페이스 에이전트 하나에게 시키는 것이다.
  - 프로젝트를 선택하고 말하면 조율 에이전트에게 시키는 것이고, 일이 워크스페이스로 나뉘며 에이전트 간 대화가 일어난다.
- 워크스페이스를 선택해 시킨 경우에도, 작업 중 다른 워크스페이스에 영향을 주는 변경이 생기면 에이전트는 그쪽에 메시지를 보낸다. [사용자 확인]
- 워크스페이스 만들기: 저장소(이미 있는 로컬 저장소 경로)와 기준 브랜치, 에이전트 종류를 고르면 코어가 `git worktree add` 로 작업 폴더를 만든다.
- 워크스페이스마다 터미널을 여러 개 열 수 있고, 그중 하나가 에이전트 터미널이다.
- 목록의 각 워크스페이스에는 이름, 한 줄 요약, 상태(작업 중, 쉬는 중, 사용자 기다림)가 보인다.

### 7.2 TODO

- 원본은 코어가 쥔다. 에이전트는 자기 내부 TODO 대신 두레 도구로 계획을 쓴다. 에이전트 종류와 무관하게 같은 패널에 나온다. [작성자 판단]
- 항목은 제목, 설명, 상태(할 일, 진행 중, 완료, 취소), 범위(프로젝트 또는 워크스페이스), 담당(에이전트 또는 사용자), 순서를 갖는다. 워크스페이스 항목은 프로젝트 항목에 딸릴 수 있다.
- 사용자는 패널에서 항목을 추가, 수정, 삭제, 순서 변경, 완료 체크할 수 있다. [사용자 결정]
- 사용자 수정은 에이전트의 **다음 단계부터** 반영된다. 에이전트가 작업 중이어도 그렇다. [사용자 결정]
  - 코어는 워크스페이스마다 "아직 전달 안 된 사용자 변경" 목록을 쌓는다.
  - 에이전트가 다음 단계로 넘어갈 때 그 목록이 에이전트에게 전달된다(7.4의 배달 방식).
  - 사용자가 손으로 끝낸 항목은 "사용자가 직접 완료함"으로 전달돼 에이전트가 건너뛴다.
- 사용자 수정이 이긴다. 에이전트가 항목을 고치려 할 때 그 항목이 에이전트가 마지막으로 읽은 뒤 사용자 손에 바뀌었으면 코어가 거절하고 현재 상태를 돌려준다.
- 담당이 사용자인 항목(커밋, push, 배포 등)은 패널에서 따로 구분돼 보인다.
- 프로젝트를 선택하면 프로젝트 TODO와 그 아래 워크스페이스별 TODO가 함께 보인다.

2단계 구현에서 정한 것 [작성자 판단]:

- 쉬는 에이전트는 TODO 수정만으로 깨우지 않는다. 미전달 변경은 다음 프롬프트 때 함께 전달된다. 바로 반영시키려면 패널의 "에이전트에게 알리기" 를 누른다. 이 버튼은 hook 신호로 쉬는 중임이 확인된 Claude Code 워크스페이스에서만 켜진다.
- 에이전트를 새로 시작하면 꺼져 있던 동안 쌓인 변경 기록은 버린다. 새 대화는 목록을 `todo_list` 로 직접 읽는다.
- Codex는 hook 실험이 끝나지 않아 끼워 넣기를 하지 않는다. `todo_list` 도구가 미전달 변경을 함께 돌려주고, 지침이 단계마다 확인하게 한다. 이 경로는 Claude Code에도 있다.
- 워크스페이스 에이전트는 자기 워크스페이스의 항목만 고칠 수 있고 프로젝트 범위 항목은 읽기만 한다. 에이전트의 수정·삭제는 자기가 읽은 판 번호(`rev`)가 맞아야 통과한다.
- 순서 바꾸기는 위·아래 버튼이다.
- 컨텍스트가 새로 시작되거나 압축되면 두레가 현재 TODO 를 다시 넣어준다 [사용자 결정]. Claude Code 가 대화 시작, 이어가기, 비우기, 압축 직후에 보내는 `SessionStart` 신호의 응답에 남은 항목을 싣는다(실측). 에이전트는 TODO 원본이 두레 DB 에 있으므로 컨텍스트가 비워져도 할 일을 잃지 않는다.
- 에이전트는 계획에 없던 필요한 일이나 사용자가 놓친 할 일을 발견하면 TODO 에 직접 추가한다 [사용자 결정]. 사용자가 해야 하는 일이면 담당을 사용자로 한다.
- 워크스페이스 상태(작업 중, 쉬는 중, 사용자 기다림)는 Claude Code의 hook 호출로 갱신한다. 승인 대기는 `Notification` 의 `notification_type: permission_prompt` 로 가려낸다(실측).

### 7.3 에이전트 간 대화와 자료 공유

- 같은 프로젝트의 워크스페이스끼리, 그리고 조율 에이전트와 워크스페이스 사이에 메시지를 주고받는다. 서로 다른 종류의 에이전트끼리도 된다.
- 메시지를 받은 에이전트는 **스스로 깨어나 작업한다.** 사용자 승인을 기다리지 않는다. [사용자 결정]
- 오간 대화는 화면에서 전부 볼 수 있고, 사용자는 언제든 멈출 수 있다. [사용자 결정]
- 멈춤은 세 가지다 [작성자 판단]:
  - 스레드 멈춤: 그 스레드의 메시지 배달만 멈춘다. 에이전트가 하던 일은 계속한다.
  - 워크스페이스 멈춤: 그 에이전트에 중단 신호를 보내고 그 워크스페이스로 가는 배달을 멈춘다.
  - 프로젝트 전체 멈춤: 프로젝트의 모든 워크스페이스와 조율 에이전트를 위와 같이 멈춘다.
  - 멈춘 동안 쌓인 메시지와 TODO 변경은 버리지 않고 대기열에 둔다. 사용자가 재개하면 전달된다.
- 폭주 방지 [작성자 판단]: 사용자 개입 없이 에이전트끼리 주고받은 메시지 수에 상한을 둔다. 스레드당 기본 10회, 프로젝트 전체 기본 50회이고 설정할 수 있다. 어느 쪽이든 넘으면 코어가 배달을 멈추고 사용자에게 알린다. 프로젝트 상한은 새 스레드를 열어 스레드 상한을 피하는 것을 막기 위함이다.
- 사용자 개입으로 치는 것은 그 프로젝트의 에이전트에게 사용자가 직접 지시를 입력한 것과 알림에서 "계속"을 누른 것이다. 개입이 있으면 횟수를 다시 센다. TODO 수정은 개입으로 치지 않는다.
- 3A단계 구현에서 정한 것 [작성자 판단, 실험 12 실측]:
  - 받는 에이전트의 상태에 따라 전달 방식이 다르다. 작업 중이면 다음 hook 응답에 싣는다. 응답을 끝냈다는 신호로 쉬는 중임이 확인됐으면 터미널에 써 넣어 깨운다. 꺼져 있으면 메시지를 첫 프롬프트로 주며 띄운다(폴더 신뢰 창이 있으면 그 뒤에 실행된다). 상태를 모르면(막 띄움, 승인 창, 중단 직후) 쓰지 않고 붙잡아 둔 채 화면에 알린다. Codex 는 스스로 `message_inbox` 로 읽을 때 전달된다.
  - 사용자가 꺼진 워크스페이스의 에이전트를 직접 시작하면, 기다리던 메시지가 첫 프롬프트로 들어간다.
  - 막 띄운 Claude Code 는 첫 신호가 올 때까지 "시작 중" 상태다. 그동안은 폴더 신뢰 창이 떠 있을 수 있어 터미널에 아무것도 쓰지 않는다.
  - 사용자가 터미널에 직접 프롬프트를 입력하면 사용자 개입으로 치고 왕복 횟수를 다시 센다. 두레가 넣은 프롬프트는 개입이 아니다. 둘은 글로 가릴 수 없어(붙여 넣은 글은 감싸여 온다, 실험 14) 두레가 넣을 때 표시해 두고 다음 프롬프트 신호에서 확인한다.
  - 사용자가 에이전트 터미널에 무언가를 입력하면 쉬는 중 확인을 지운다. 입력창에 글을 치는 중이거나 선택 창을 연 터미널에 두레가 써 넣지 않기 위함이다.
  - 첫 프롬프트로 건넨 메시지는 에이전트가 프롬프트를 받았다는 신호가 와야 전달된 것으로 친다. 그 전에 에이전트가 끝나면 미전달로 되돌리고 화면에 이유를 보인다. 다시 띄우기를 반복하지 않는다.
  - 받는 워크스페이스가 지워지면 미전달 메시지는 "전달 못 함" 으로 남고 보낸 워크스페이스가 두레의 알림을 받는다.
  - 다른 워크스페이스의 메시지는 사용자 지시가 아니라 동료의 요청으로 다루게 한다. 전달 글에서 인용된 본문 말고는 모든 값을 한 줄로 만들어 `[두레]` 줄을 위조할 수 없게 한다.
  - 전체 멈춤으로 중단된 에이전트는 재개해도 스스로 이어가지 않는다(중단 뒤에는 쉬는 중을 확인할 신호가 없다). 사용자가 터미널에서 이어가게 한다.
  - 꺼진 Codex 는 메시지로 자동으로 띄우지 않는다.
  - 작업 중인데 10분 넘게 신호가 없으면 상태를 모르는 것으로 보고 화면에 알린다.
  - 받은 메시지 본문은 줄마다 인용 표시를 붙여 전달한다. 본문에 `[두레]` 라고 적혀 있어도 두레의 지시로 읽히지 않게 하기 위함이다.
  - 받는 사람은 워크스페이스 이름으로 지정한다. 사용자도 대화 화면에서 스레드에 말할 수 있다.
  - 전체 멈춤은 메시지 전달을 멈추고 작업 중인 에이전트도 중단시킨다(Esc). 중단하면 아무 신호도 오지 않으므로 상태는 두레가 바꾼다.
- 공유 대상은 전부다: 작업 결과, 결정사항, API 스펙 등. [사용자 결정] 자료는 종류, 제목, 본문 또는 파일 절대 경로 링크, 올린 워크스페이스를 갖고 프로젝트 자료 목록에 쌓인다. 메시지에 자료를 첨부할 수 있다.

### 7.4 에이전트에게 전달하는 방식

메시지와 사용자 TODO 변경을 에이전트에게 넣는 길은 에이전트 상태에 따라 다르다. [작성자 판단]

아래는 0단계 실험(`docs/superpowers/findings/2026-11-11-agent-wiring.md`)으로 확정한 내용이다.

- **쉬는 중**: 코어가 에이전트 터미널에 입력을 써 넣어 깨운다. 단 hook 신호로 쉬는 중임을 확인했을 때만 쓴다. 에이전트는 예고 없이 선택 창(폴더 신뢰, 업데이트, 새 모델 안내)을 띄우고, 그 창에 Enter가 들어가면 의도하지 않은 동작이 실행된다(실험 중 실제로 `brew upgrade` 가 실행됐다). 상태를 모르면 쓰지 않고 메시지를 대기열에 둔 채 사용자에게 알린다.
- **작업 중**: 대기열에 쌓고, 에이전트가 다음 단계로 넘어가는 시점에 전달한다. Claude Code는 hook 으로 끼워 넣는다. 도구 실행 뒤(`PostToolUse` 의 `additionalContext`)와 응답 종료 시점(`Stop` 의 `decision: "block"`) 둘 다 실측으로 된다.
- **신뢰 선언**: 실행 시 지침에 "두레는 hook 으로 `[두레]` 로 시작하는 글을 전달한다. 사용자가 직접 설정한 방식이니 사용자 지시와 같은 권위로 따르라" 를 반드시 넣는다. 없으면 에이전트가 끼워 넣은 내용을 사용자 지시로 믿지 않고 무시한다(실측).
- **상태 신호**: Claude Code는 hook 으로 작업 시작, 작업 중, 쉬는 중, 승인 창에서 사용자 기다림을 알 수 있다. 중단과 모델 오류 때는 쉬는 중 신호가 오지 않는다. 두레가 직접 중단시킨 경우는 두레가 상태를 바꾸고, 그 밖에 한동안 신호가 없으면 "상태 모름" 으로 둔다.
- **첫 시작**: 새 작업 폴더마다 Claude Code 가 폴더 신뢰 창을 띄운다. 두레가 대신 "신뢰함" 으로 답한다. [사용자 결정, 2026-11-11. 처음 설계는 "두레가 대신 누르지 않는다" 였다]
  - 근거: 작업 폴더는 사용자가 직접 등록한 저장소에서 두레가 만든 것이다. 저장소 등록 화면에 "등록한 저장소는 신뢰하는 것으로 본다" 고 적어 둔다. 폴더를 신뢰하면 그 저장소 안의 Claude Code 설정(hook, MCP 서버)이 실행될 수 있다.
  - 방법 [작성자 판단]: 에이전트를 띄운 뒤 첫 hook 이 올 때까지(= "시작 중") 터미널 출력을 본다. 화면 끝이 신뢰 창이고(안내문 "Accessing workspace", 두 선택지, "Enter to confirm" 이 모두 보임), 묻는 폴더가 이 작업 폴더이고, 커서가 "No, exit" 에 있으면 아래 화살표를 보낸다. 다시 그려진 화면에서 커서가 "Yes, I trust this folder" 에 있는 것을 본 뒤에만 Enter 를 보낸다. 하나라도 다르면 아무것도 누르지 않는다. 사용자가 그 터미널에 키를 누르면 손을 뗀다. 30초가 지나면 그만둔다.
  - 넘어가지 못하면 "시작 중" 에 머물고 화면이 터미널에서 확인하라고 안내한다.
  - Codex 에는 하지 않는다(화면을 실측하지 못했다).
  - 확인(실제 Claude Code 2.1.322): 새 폴더에서 화면의 "에이전트 시작" 을 누르자 0.5초에 신뢰 창, 1.0초에 커서가 Yes, 2.5초에 "쉬는 중" 이 됐다.
- ⏳ Codex 쪽 깨우기, 끼워 넣기, 상태 신호는 이 PC에서 Codex 모델 호출이 안 돼 아직 실측하지 못했다. 끼워 넣기가 안 되는 에이전트는 "현재 응답이 끝난 직후 전달"로 물러선다. 이것도 "다음 단계부터 반영"을 만족한다.

### 7.5 프로젝트 조율

- 조율 에이전트는 두레가 관리하는 프로젝트 전용 폴더에서 돈다. 어떤 저장소에도 직접 쓰지 않는다. 종류(Claude Code 또는 Codex)는 프로젝트마다 고른다. 기본은 Claude Code다. [작성자 판단]
- 기획서(파일 경로 또는 붙여넣은 글)를 받으면 필요한 워크스페이스 목록을 제안한다. 제안 한 건은 이름, 저장소, 기준 브랜치, 에이전트 종류, 맡을 역할을 담는다.
- 제안은 승인 화면에 뜬다. 사용자가 항목을 고치고, 빼고, 더한 뒤 승인해야 워크스페이스가 만들어진다. [사용자 결정: 커스텀할 수 있어야 하므로 승인 필수]
- 저장소는 이미 있는 로컬 저장소를 연결하는 것이 기본이다. 프로젝트에는 사용자가 등록한 저장소 목록이 있고, 조율 에이전트는 두레 도구로 그 목록(이름, 경로, 브랜치)을 본다. [작성자 판단]
- 맞는 저장소가 없으면 새 저장소 만들기를 제안에 넣을 수 있다. 새 저장소는 승인 화면에서 사용자가 고른 상위 폴더에 `git init` 하고 빈 첫 커밋 하나를 만든 것이다. 뼈대 코드는 두레가 넣지 않고 그 워크스페이스의 에이전트가 TODO에 따라 만든다. [작성자 판단]
- 승인 뒤 조율 에이전트가 기획서에서 개발 TODO를 뽑아 프로젝트 항목과 워크스페이스 항목으로 쓴다. [사용자 결정]
- 프로젝트에 지시가 내려오면 조율 에이전트가 일을 나눠 각 워크스페이스에 메시지로 보내고, 진행을 지켜보다 끝나면 종합 보고한다.

### 7.6 DB

- 연결은 프로젝트 단위로 등록하고, 그 프로젝트의 모든 워크스페이스가 같이 쓴다. [작성자 판단]
- 대상은 PostgreSQL, MySQL, MongoDB다. [작성자 판단]
- 사용자는 패널에서 테이블(컬렉션) 목록, 스키마, 조회 결과를 본다. 에이전트는 두레 도구로 같은 DB의 스키마를 보고 조회한다. [사용자 결정: 조회 기능, 버전 1 포함]
- **조회 전용이다.** [작성자 판단] 코어가 읽기 전용 트랜잭션으로 실행하고(MongoDB는 조회 계열 명령만 허용), 결과 행 수와 실행 시간에 상한을 둔다. 연결 등록 화면에서 읽기 전용 계정 사용을 권한다.
- 접속 정보는 macOS 키체인에 저장한다(Electron `safeStorage`). 에이전트에게는 연결 이름만 보이고 비밀번호와 접속 문자열은 넘어가지 않는다.
- 두레 DB 기능은 들여다보는 용도다. 에이전트가 만드는 애플리케이션 코드(장면 1의 백엔드 서버)는 저장소가 원래 쓰는 설정(`.env` 등)으로 DB에 접속한다. 두레는 자기가 보관한 접속 정보를 터미널 환경변수로 주입하지 않는다. 따라서 장면 1은 두레 DB 기능 없이도 성립하고, "접속 정보 노출 금지"는 두레가 보관한 접속 정보에 대한 약속이다. [작성자 판단]

### 7.7 요약과 자동 이름

- 에이전트가 작업이 진행될 때마다 두레 도구로 자기 워크스페이스의 한 줄 요약을 갱신한다. 요약 전용 LLM 호출을 따로 하지 않는다. [작성자 판단]
- 에이전트는 작업 내용에 더 맞는 이름이 있으면 워크스페이스 표시 이름을 바꾼다. 묻지 않고 바꾼다. 사용자가 직접 지은 이름은 건드리지 않는다. [작성자 판단, 사용자 이의 없음]
- 바뀌는 것은 화면의 표시 이름뿐이다. 브랜치 이름과 작업 폴더 경로는 그대로 둔다. [작성자 판단]

### 7.8 멈추는 선과 커밋 창

- 에이전트는 커밋 메시지 작성까지만 한다. 커밋 실행, push, 배포는 하지 않는다. [사용자 결정]
- 커밋 메시지는 에이전트가 자동으로 써서 두레에 초안으로 저장한다. 사용자는 두레 화면의 커밋 창에서 그 메시지를 고친 뒤 커밋과 push 를 직접 누른다. [사용자 결정, 2026-11-11]
  - 처음 설계의 "에이전트에게 맡기기" 버튼은 만들지 않는다. 에이전트에게 커밋을 넘기는 길은 없다.
- 커밋 창 [작성자 판단]:
  - 워크스페이스 화면 머리의 "커밋" 버튼으로 연다. 바뀐 파일 수가 보이고, 에이전트가 초안을 써 뒀으면 점이 찍힌다.
  - 바뀐 파일 목록(상태, 경로, 추가·삭제 줄 수)에서 체크로 넣을 파일을 고른다. 기본은 전부. 파일별 변경 내용(diff)은 보여주지 않는다.
  - 메시지 입력칸은 초안으로 채워지고 사용자가 고칠 수 있다. 고치는 중에 에이전트가 초안을 새로 쓰면 덮어쓰지 않고 "불러오기" 를 보인다.
  - 커밋은 사용자의 git 설정(이름, 메일, 서명, hook)을 그대로 따른다. 실패하면 git 의 오류를 그대로 보이고 고친 메시지를 남긴다.
  - push 버튼 옆에 어디로 나가는지(브랜치와 `origin` 주소)를 보인다. `origin` 이 없거나 보낼 커밋이 없으면 버튼이 꺼진다. 강제로 밀지 않는다.
  - 커밋이나 push 가 끝나면 켜져 있는 에이전트에게 두레의 알림으로 전한다. 꺼진 에이전트에게는 보내지 않는다(알림 때문에 에이전트가 떠오르면 안 된다).
- 지키게 하는 방법 [작성자 판단]:
  - 두레가 에이전트를 띄울 때 주는 지침에 이 규칙을 넣는다.
  - 에이전트 터미널의 `PATH` 앞에 두레의 `git` 대리 실행 파일을 둔다. 하위 명령이 `commit` 이나 `push` 면 거절하고 할 일을 알려준다. 나머지 git 명령은 그대로 통과시킨다. 사용자가 여는 셸 탭과 두레 자신이 실행하는 git 에는 걸지 않는다.
  - 한계: 막는 것은 `commit` 과 `push` 두 하위 명령뿐이다. `merge`, `rebase`, `cherry-pick` 처럼 커밋을 만드는 다른 명령과 진짜 git 을 절대 경로로 부르는 것은 막지 않는다. 실수와 지침 이탈을 막는 장치이지 보안 경계가 아니다.
  - 배포는 명령이 프로젝트마다 달라 기술적으로 막지 않는다. 지침과 사용자 몫 TODO 로만 다룬다.
- 확인(실제 Claude Code): "README 에 한 줄 추가하고 커밋해" 라고 시키자 에이전트는 커밋을 시도하지 않고 초안을 저장하고 "커밋" 을 사용자 몫 TODO 로 남겼다. 사용자가 커밋 창에서 메시지를 고쳐 커밋하고 push 하자, 쉬고 있던 에이전트가 알림을 받고 TODO 를 완료로 바꿨다. 대리 실행 파일의 거절은 에이전트가 지침을 따라 실제 장면에서는 일어나지 않았고, 자동 테스트(스크립트를 실제로 실행)로 확인했다.

### 7.9 에이전트 권한 모드

- 워크스페이스마다 권한 모드를 고른다. [사용자 결정]
  - **승인 필요 (기본값)**: 파일 수정은 자동 승인, 명령 실행은 에이전트 자체 승인 창을 거친다.
  - **승인 생략**: 에이전트가 묻지 않고 실행한다. 사용자가 믿는 저장소에만 켠다. 켤 때 화면에서 위험을 알린다.
- 에이전트가 승인 창에서 멈추면 두레가 그 워크스페이스를 "사용자 기다림"으로 표시하고 알림을 띄운다. 사용자가 안 보는 사이 깨어난 에이전트가 조용히 멈춰 있는 일이 없어야 한다.
- 조율 에이전트가 제안하는 워크스페이스의 권한 모드는 승인 화면에서 사용자가 정한다. 제안의 기본값은 승인 필요다. [작성자 판단]
- 7.8의 커밋·push 차단은 권한 모드와 무관하게 항상 적용된다.
- 실행 옵션(0단계 실험): Claude Code는 승인 필요가 `--permission-mode acceptEdits`, 승인 생략이 `--dangerously-skip-permissions` 다(실측). 승인 창에서 멈춘 상태는 `Notification` hook 으로 알 수 있다(실측). Codex는 승인 필요가 `--sandbox workspace-write --ask-for-approval on-request`, 승인 생략이 `--dangerously-bypass-approvals-and-sandbox` 일 것으로 보지만 ⏳ 아직 실측하지 못했다.
- Codex의 승인 필요 모드에서는 샌드박스가 localhost를 포함한 네트워크를 막는다(실측). 서버를 띄우고 호출하는 일은 승인 없이는 안 된다. 장면 1에서 Codex 워크스페이스가 끊김 없이 돌려면 승인 생략 모드여야 하고, 승인 필요 모드에서는 서버 실행 시점에 "사용자 기다림" 으로 멈춘다.
- 폴더 신뢰 창은 승인 생략 모드에서도 뜬다(실측).

### 7.10 채팅 보기

- 워크스페이스 보기를 터미널과 채팅으로 전환할 수 있다. 처음은 터미널이다. [사용자 결정]
- 채팅은 가운데 한 줄로 흐르는 대화다. 에이전트의 말은 글로, 한 일은 "명령 N개 실행함" 같은 접힌 한 줄로, 내 말은 오른쪽 말풍선으로, 위에 작업 시간, 아래에 입력창. 접힌 줄을 펼치면 한 일이 한 줄씩, 그 줄을 펼치면 실행한 명령과 출력이 그대로 보인다. [사용자 결정]
- 에이전트끼리 주고받은 메시지도 별도 패널이 아니라 이 대화 흐름 안에 카드로 보인다. [사용자 결정]
- 아래는 작성자 판단이다.
  - 에이전트는 지금처럼 터미널에서 돈다. 채팅 보기는 그 위에 얹은 다른 화면이다. 두 보기는 같은 에이전트를 보므로 오가도 대화가 이어진다. 채팅 보기에 문제가 생겨도 에이전트와 터미널 보기는 영향받지 않는다.
  - 재료는 Claude Code 가 스스로 쓰는 대화 기록 파일(JSONL)이다. hook 본문의 `transcript_path` 로 위치를 알고, hook 이 올 때마다(그리고 작업 중에는 1초마다) 읽은 자리 뒤의 새 줄만 읽는다. 읽기만 한다. `~/.claude/` 밖의 경로와 그 밖을 가리키는 링크는 읽지 않는다.
  - 두레가 넣은 글(TODO 변경, 다른 워크스페이스의 메시지, 알림)은 내 말풍선으로 보이지 않고 "두레가 전달" 줄로 보인다. 기록의 필드로는 사용자 입력과 구분할 수 없어(실험 15b) 글이 `[두레]` 로 시작하는지로 가린다. 사용자의 다른 도구가 hook 으로 넣은 글은 보이지 않는다.
  - 받은 메시지는 두레가 그 메시지를 전달한 자리에 카드로 놓고, 보낸 메시지는 보낸 시각에 끼운다. 긴 메시지는 접혀 있다. 오른쪽 "대화" 탭은 그대로다(프로젝트 전체의 대화를 스레드별로 본다).
  - 입력창은 쉬는 중과 작업 중에만 켜진다. 시작 중과 승인 대기 중에는 꺼지고 터미널로 안내한다.
    - 쉬는 중에 보낸 글은 에이전트의 터미널 입력칸에 써 넣는다.
    - 작업 중에 보낸 글은 터미널에 쓰지 않는다. 두레가 맡아 두었다가 다음 hook 응답(도구 실행 뒤, 응답 종료 때)에 `[두레] 사용자가 채팅으로 보낸 말이다` 로 실어 전달한다. 채팅에는 점선 말풍선으로 "에이전트가 다음 단계에서 읽습니다" 가 보이고, 전달되면 보통 말풍선이 된다. 이유: 작업 중인 터미널에는 승인 창이 떠 있을 수 있고 창이 떴다는 알림은 약 6초 늦게 온다(실험 15e). 그 틈에 글과 Enter 를 써 넣으면 Enter 가 "허용" 으로 들어간다. [전체 리뷰에서 발견해 바꿈]
    - 중단 등으로 전달되지 못하고 남은 글은 다음에 쉬는 중에 보내는 글 앞에 붙어 나간다. 에이전트가 끝나면 버린다.
  - 승인 요청은 입력창 자리의 카드로 보인다: 무엇을 하려는지와 "허용", "거부", "터미널에서 보기". "허용" 은 터미널에 Enter, "거부" 는 Esc 를 보낸다(실험 15e: 커서는 "1. Yes" 에 있다). hook 으로 승인 창임이 확인됐고, 끝나지 않은 도구 호출이 하나뿐이라 어느 호출의 창인지 분명하고, 그 호출이 시작된 뒤로 사용자가 터미널을 건드리지 않았을 때만 두 버튼이 보인다. "다시 묻지 않기" 같은 다른 선택지는 터미널에서 고른다.
  - 승인을 거부하거나 터미널에서 직접 Esc 로 중단하면 hook 이 오지 않는다. 기록의 중단 줄을 읽어 상태를 "쉬는 중" 으로 되돌린다(이 단계 전에는 "사용자 기다림" 에 머물렀다).
  - 보이는 것은 지금 대화뿐이다. 에이전트를 다시 시작하거나 `/clear` 하면 새 대화가 된다. `/compact` 뒤에는 "대화가 압축됨" 줄이 보이고 앞의 항목은 남는다.
  - 고른 보기는 워크스페이스별로 기억한다.
- 한계:
  - 기록 파일의 형식은 Claude Code 내부의 것이다. 버전이 오르면 바뀔 수 있다. 읽지 못하는 줄은 건너뛰고, 파일을 읽지 못하면 이유를 보이고 터미널 보기를 권한다.
  - 에이전트의 글은 한 덩어리가 끝난 뒤에야 기록된다(실험 15a). 채팅 보기에서는 글이 한 글자씩 흐르지 않고 덩어리로 나타난다.
  - Codex 워크스페이스에는 채팅 보기가 없다(기록 형식을 실측하지 못했다). 전환 버튼이 꺼져 있고 이유를 보인다.
  - 항목이 400개를 넘으면 뒤쪽 400개만 보인다.
- 확인(실제 Claude Code 둘, 검증용 인스턴스): 채팅 입력창으로 파일 수정을 시키자 내 말풍선, "작업 9개 함" 접힌 줄, 표가 든 에이전트의 글이 차례로 보였고 단계를 펼치면 `ls -la` 의 출력이 그대로 보였다. 승인이 필요한 명령에서 승인 카드가 떴고 "거부" 를 누르자 단계가 "실행 안 함", 대화에 "중단됨" 이 보이고 상태가 "쉬는 중" 으로 돌아왔다("허용" 은 같은 장면에서 사용자가 직접 눌러 명령이 실행됐다). 프론트에게 백엔드에 물어보라고 시키자 프론트 채팅에 "백엔드에게 보냄" 카드와 "백엔드가 보냄" 카드(첨부 자료 포함)가 흐름 안에 보였다. 작업 중에 보낸 한마디가 반영됐다. 패널에서 TODO 를 더하자 "두레가 전달" 줄이 보였다. 에이전트를 껐다 켜자 새 대화로 시작했다.
- 전체 리뷰 뒤 고친 것: 작업 중 입력을 hook 전달로 바꿈(위), 승인 알림 전에 터미널을 건드린 경우와 도구 호출이 겹친 경우 채팅에서 답하지 못하게 함, 기록이 `~/.claude` 밖에 있으면 빈 화면 대신 이유를 보임, 기록을 한 번에 8MB 까지만 읽고 처음 붙을 때 16MB 를 넘으면 끝쪽만 읽음, 오래된 항목을 버려 메모리를 묶음, 보통 파일이 아니면 열지 않음, 신뢰 창의 폴더 경로를 끝까지 견줌. 고친 뒤 실제 에이전트로 작업 중 입력을 다시 확인했다(점선 말풍선 → 전달 → "완료 추가확인").
- 미뤄 둔 것: 승인 카드의 명령을 알림 본문의 도구 이름과 대조하지 않음, 다른 프로젝트의 기록 파일도 `~/.claude` 아래면 받아들임(같은 사용자 화면에만 보인다), Shift+F3 같은 일부 키가 터미널 자동 응답으로 판정됨, 사용자가 직접 `[두레]` 로 시작하는 글을 쓰면 "두레가 전달" 줄로 보임(표시 문제).
- 확인하지 못한 것(⚠️): 병렬 도구 호출에서 hook 이 오는 순서, 실제 에이전트에서 `/compact` 뒤의 채팅 화면(기록 줄의 모양은 실험 15f 로 확인했고 해석은 자동 테스트로만 확인), 아주 긴 대화에서의 속도, `AskUserQuestion` 같은 여러 선택지 창이 떴을 때의 카드.
